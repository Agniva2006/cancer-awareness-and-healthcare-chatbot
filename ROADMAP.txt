--------------------------------------------------------------------------------
1.2 WHY POSTGRESQL (THE DECISION)
--------------------------------------------------------------------------------
You asked: SQL or NoSQL? ANSWER: PostgreSQL. Here is the reasoning a senior
engineer would give:

  + ACID transactions — money (orders, subscriptions) MUST be exact. A
    NoSQL database with eventual consistency can lose a payment record.
  + Foreign keys & joins — user -> order -> plan -> quota relationships
    are natural in SQL. In MongoDB you'd model them manually.
  + JSONB — PostgreSQL's JSONB columns give you document flexibility for
    chat messages and retrieved context. You do NOT need MongoDB.
  + pgvector extension — stores AI embeddings for semantic search INSIDE
    Postgres. You do NOT need a separate vector DB (Qdrant/Pinecone) yet.
  + One system to learn, backup, and secure.

  What you WILL add later (Phase 5): Redis — as a cache for identical
  questions and rate-limit counters. That's the NoSQL piece you actually need.

--------------------------------------------------------------------------------
2.2 THE FLOW YOU MUST UNDERSTAND (MEMORIZE THIS)
--------------------------------------------------------------------------------

  REGISTRATION:
    client -> POST /auth/register {email, password, full_name}
           -> validate (email format, password policy)
           -> check email not already taken
           -> hash password with bcrypt (NEVER plaintext, NEVER MD5/SHA)
           -> insert user (is_active=True, is_verified=False)
           -> send verification email (token valid 24h)
           -> return 201

  LOGIN:
    client -> POST /auth/login {email, password}
           -> look up user by email
           -> bcrypt.checkpw(input, stored_hash)   (constant-time compare)
           -> issue TWO tokens:
                ACCESS TOKEN  (JWT, 15 min expiry, stateless)
                REFRESH TOKEN (opaque random string, 7-30 days, stored hashed
                               in sessions table, stateful)
           -> return both

  EVERY PROTECTED REQUEST:
    client -> GET /ask with "Authorization: Bearer <access_token>"
           -> verify JWT signature + expiry
           -> load user from DB (check is_active)
           -> process request

  ACCESS TOKEN EXPIRED:
    client -> POST /auth/refresh {refresh_token}
           -> look up token hash in sessions table
           -> check not expired, not revoked
           -> ROTATE: revoke old row, create new session row
           -> issue new access + refresh tokens

  LOGOUT:
    client -> POST /auth/logout with refresh token
           -> set revoked_at on that session row
           -> client deletes tokens from storage

  WHY TWO TOKENS? (this is the key interview question)
    - Access token leaks? It dies in 15 minutes. Damage limited.
    - Refresh token leak? Server can revoke it (it's in the DB).
    - Stateless JWT access tokens mean no DB hit on every request — fast.
    - Stateful refresh tokens mean revocable sessions — secure.

3.1 GOAL
--------------------------------------------------------------------------------
Freemium monetization: Free tier with monthly quota, paid tiers with more
features. Payments handled 100% by the provider; your server only reacts to

--------------------------------------------------------------------------------
3.2 THE THREE GOLDEN RULES
--------------------------------------------------------------------------------
  1. NEVER store card numbers — the provider (Stripe/Razorpay) handles them
     on their hosted page. You never see them. PCI compliance is theirs.
  2. NEVER trust the frontend for pricing — the server defines plan prices
     from config; the frontend just shows buttons.
  3. WEBHOOKS ARE THE SOURCE OF TRUTH — activate a subscription ONLY when the
     provider's webhook arrives (with a verified signature), never from a
     frontend redirect (which can be faked).

--------------------------------------------------------------------------------
3.3 PROVIDER CHOICE
--------------------------------------------------------------------------------
  Stripe        -> best docs, global, excellent test mode, use this if your
                   audience is international
  Razorpay      -> best for India (UPI, RuPay, local cards)
  Paddle/LemonSqueezy -> "merchant of record" — they handle global tax/VAT
                         for you (worth it if selling worldwide and you don't
                         want to deal with tax compliance)

--------------------------------------------------------------------------------
3.4 THE PAYMENT FLOW (STRIPE EXAMPLE)
--------------------------------------------------------------------------------

  1. User clicks "Upgrade to Pro" on your pricing page
  2. Frontend -> POST /billing/checkout {plan_code: "pro"}
  3. Server:
       - Verifies user is authenticated
       - Gets/creates Stripe Customer for this user (store customer_id)
       - Creates a Checkout Session with:
           * price ID for the "pro" plan (from env/DB)
           * success_url, cancel_url
           * metadata: {user_id, plan_code}
       - Returns session URL
  4. Frontend redirects user to that URL (Stripe-hosted payment page)
  5. User pays
  6. STRIPE SENDS WEBHOOK to your server: POST /billing/webhooks/stripe
  7. Server:
       - VERIFIES SIGNATURE (critical! prevents forged requests)
       - Checks event hasn't been processed before (idempotency — Stripe can
         send the same event twice)
       - Updates subscriptions table: status=active, period dates
       - Records the order as paid
       - Grants entitlements (quota reset, features unlock)
  8. Frontend success page -> polls /auth/me which now shows plan "pro"

  WEBHOOK EVENTS TO HANDLE:
    checkout.session.completed        -> subscription created
    customer.subscription.updated     -> plan change, renewal, cancel_at_end
    customer.subscription.deleted     -> subscription ended
    invoice.payment_failed            -> dunning: mark past_due, notify user
    invoice.paid                      -> renewal confirmed

4.3 RETRIEVAL UPGRADE: TF-IDF -> HYBRID SEMANTIC SEARCH
--------------------------------------------------------------------------------
Current: TF-IDF (keyword matching). Misses synonyms ("my scan came back" won't
match "imaging results").

Upgrade to HYBRID:
  1. Dense/semantic: embed each article with SentenceTransformers
     all-MiniLM-L6-v2 (free, runs locally, 384 dims — matches your schema)
     - Store embeddings in knowledge_documents.embedding (pgvector)
     - Query: embed the question, cosine similarity search
  2. Sparse/keyword: TF-IDF or BM25 (keep what you have)
  3. FUSION: Reciprocal Rank Fusion (RRF)
     score = sum(1 / (60 + rank_i)) for each list
     - Gives the best of both worlds: semantic understanding + exact medical
       term matching ("EGFR exon 19 deletion" needs exact match)

  CHUNKING: articles longer than ~300 tokens -> split into overlapping chunks
  (keep the title with each chunk). Store chunk-level embeddings.

  EMBEDDING RECOMPUTE: whenever you add/update a knowledge article, recompute
  its embedding (do it in the seed script or on save).

--------------------------------------------------------------------------------
4.4 CHATBOT UPGRADES
--------------------------------------------------------------------------------
  a. SYSTEM PROMPT (lung cancer specialist):
     "You are OncoLung, a lung cancer information assistant for patients and
     clinicians. You answer ONLY from the provided context. If the context is
     insufficient, say so honestly. Never diagnose, never prescribe, never
     give personal treatment advice. Cite the source titles you used. Match
     the tone to the audience mode."

  b. CONVERSATION MEMORY:
     - Store last 6 turns in the messages table
     - Pass to LLM as context (you already pass chat_history — now persist it)
     - Add follow-up understanding: "What about stage 3?" after a stage
       question should resolve "stage 3" to the same topic.

  c. CLARIFICATION BEHAVIOR:
     Instruct the model: if the question is ambiguous (e.g., "my scan"), ask
     ONE clarifying question before answering.

  d. GROUNDING CHECK:
     - If top retrieval score < threshold -> answer "I don't have enough
       verified information about this. Please consult a qualified
       oncologist." Do NOT let the LLM freestyle on medical topics.

  e. CITE SOURCES:
     - Return the article titles used (you already do this — render them in
       the frontend as clickable chips)

  f. STREAMING (optional, big UX win):
     - Server-Sent Events (SSE) from FastAPI: stream tokens as the LLM
       generates them
     - Frontend: render progressively with a typing cursor
     - Implement after the core is solid

4.5 DEFINITION OF DONE

  [ ] "What does my scan mean?" (ambiguous) triggers a clarifying question

================================================================================
PHASE 6: LUNG CANCER DETECTION WITH DEEP LEARNING
             (Chest CT -> Nodule Detection & Classification Microservice)
================================================================================
Estimated: 4-6 weeks | Priority: ADVANCED — only after Phases 1-5 are solid

--------------------------------------------------------------------------------
6.1 GOAL
--------------------------------------------------------------------------------
A separate microservice that takes a chest CT scan (or a slice/series) and:
  1. Detects lung nodules (object detection)
  2. Classifies malignancy risk (binary: benign vs suspicious)
  3. Returns results to the main chatbot, which explains them in plain language
     with heavy disclaimers.

  THIS IS A RESEARCH/EDUCATIONAL TOOL. It is NOT a diagnostic device. Every
  result must carry: "This is experimental and not a medical diagnosis."

--------------------------------------------------------------------------------
6.2 WHY A SEPARATE MICROSERVICE
--------------------------------------------------------------------------------
  - Different runtime: needs GPU, PyTorch, huge model weights — don't slow
    down your API container
  - Different scaling: inference load != chat load
  - Different deploy cycle: you'll retrain models often
  - Communicates with the main API via REST (upload scan -> get JSON result)

--------------------------------------------------------------------------------
6.3 DATASETS (START HERE)
--------------------------------------------------------------------------------
  LIDC-IDRI (Lung Imaging Database Consortium)
    - ~1,000 chest CT scans with radiologist-annotated lung nodules
    - The gold standard for lung nodule research
    - Requires free registration (TCIA - The Cancer Imaging Archive)
    - ~120 GB (you can download subsets)

  LUNA16
    - Cleaned subset of LIDC-IDRI (removed inconsistencies)
    - 1,186 scans, ~7,000 annotated nodules
    - Standard benchmark for nodule detection
    - EASIER TO START WITH than raw LIDC

  NLST (National Lung Screening Trial)
    - Huge screening dataset, requires application
    - Better for later, not for getting started

  RECOMMENDED PATH: LUNA16 first.

--------------------------------------------------------------------------------
6.4 MODEL ARCHITECTURE (RECOMMENDED LEARNING PATH)
--------------------------------------------------------------------------------

  LEVEL 1 (start here — 2D classification):
    - Take CT slices containing nodules (crop around annotated nodules)
    - Fine-tune a pretrained 2D CNN: ResNet-50 or DenseNet-121
    - Binary classification: nodule vs no nodule (or benign vs suspicious)
    - Learn the full pipeline: data loading, augmentation, training,
      validation, inference
    - Metrics: accuracy, AUC, sensitivity, specificity

  LEVEL 2 (3D — real clinical quality):
    - 3D CNN (3D ResNet / 3D DenseNet) on nodule crops (e.g., 32x32x32)
    - Uses volumetric context — significantly better performance
    - Use PyTorch with 3D convolutions

  LEVEL 3 (full detection — the real product):
    - Object detection on full CT volumes
    - Options: RetinaNet-3D, YOLOv5-3D adaptations, or MONAI's detection API
    - MONAI (Medical Open Network for AI) — PyTorch-based framework
      purpose-built for medical imaging. USE IT. It handles DICOM parsing,
      3D transforms, sliding-window inference, and has pretrained models.

  LEVEL 4 (segmentation, advanced):
    - U-Net variants for tumor boundary delineation
    - Volumetric growth tracking (RECIST criteria)

--------------------------------------------------------------------------------
6.5 DATA PIPELINE (THE MOST IMPORTANT PART)
--------------------------------------------------------------------------------
  1. DICOM parsing: pydicom to read CT scans (HU values — Hounsfield Units)
  2. Preprocessing:
     - Normalize HU (window: lung window, e.g., -1000 to 400 HU)
     - Resample to consistent voxel spacing (e.g., 1x1x1 mm)
     - Resize/crop to standard input size
  3. Data loading: MONAI's Dataset/DataLoader with transforms
  4. Data augmentation:
     - Random flips, rotations, intensity shifts
     - BE CAREFUL: augmentation must respect medical reality (don't flip
       laterality markers)
  5. Train/val/test split: SPLIT BY PATIENT, never by slice (otherwise
     slices from the same scan leak between sets — you'll get fake metrics)

  THIS IS THE #1 BEGINNER MISTAKE: splitting by slice instead of by patient.
  Your model will look 99% accurate and be useless in reality.

--------------------------------------------------------------------------------
6.6 TRAINING SETUP
--------------------------------------------------------------------------------
  - GPU required: options
      a) Google Colab free tier (T4 GPU) — start here
      b) Kaggle Notebooks (free GPU hours)
      c) Cloud: Lambda Labs / RunPod / Vast.ai (cheap per-hour)
  - Framework: PyTorch + MONAI
  - Experiment tracking: Weights & Biases (free tier) or MLflow
    (log every run: hyperparams, metrics, loss curves — non-negotiable for
     a real ML project)
  - Hyperparameters to start:
      optimizer: AdamW, lr 1e-4, weight decay 1e-5
      batch size: 16-32 (2D) / 4-8 (3D)
      epochs: 20-50 with early stopping on validation AUC

--------------------------------------------------------------------------------
6.7 VALIDATION & METRICS (REPORT THESE HONESTLY)
--------------------------------------------------------------------------------
  - Sensitivity (recall): % of true cancers detected — MOST important
    (a missed cancer is worse than a false alarm)
  - Specificity: % of true negatives correctly identified
  - AUC-ROC: overall discriminative ability
  - Per-nodule FROC analysis (FROC = free-response ROC, standard in this field)
  - Report on a HELD-OUT test set the model NEVER saw

--------------------------------------------------------------------------------
6.8 SERVING THE MODEL
--------------------------------------------------------------------------------
  - Separate FastAPI service (detection-api/)
  - Endpoint: POST /detect (multipart file upload of a CT series/zip)
  - Steps: validate file type -> preprocess -> run inference -> return JSON:
      {
        "nodules": [
          {"location": {...}, "malignancy_probability": 0.87,
           "size_mm": 8.2, "confidence": 0.91}
        ],
        "model_version": "v1.2.0",
        "disclaimer": "..."
      }
  - Model versioning: save with MLflow/W&B, load specific version at startup
  - Latency: batch inference, consider ONNX export or TorchScript for speed
  - GPU serving: Colab won't work for production — use RunPod/Replicate/
    Hugging Face Inference Endpoints for GPU hosting

--------------------------------------------------------------------------------
6.9 LLM BRIDGE (THE MAGIC MOMENT)
--------------------------------------------------------------------------------
  When detection returns results, feed them into the chatbot:
    "The AI analysis found [N] lung nodule(s). The largest measures [X] mm
     with a malignancy probability of [Y]%. According to Fleischner Society
     guidelines, nodules of this size and profile typically require..."

  The chatbot (already grounded in your Phase 4 knowledge base) explains the
  finding, what follow-up imaging is standard, and which questions to ask the
  doctor. THIS integration — AI detection + AI explanation — is what makes
  your product unique.

--------------------------------------------------------------------------------
6.10 REGULATORY & ETHICAL REALITY CHECK (READ THIS)
--------------------------------------------------------------------------------
  - A DL model that outputs "cancer yes/no" on real patient scans IS a medical
    device under FDA/EU MDR rules. You cannot ship that as a consumer app.
  - Safe positioning:
      * "Educational/research demonstration only"
      * "Not a medical diagnosis — consult a radiologist"
      * Synthetic or publicly-available (LUNA16) scans only, no real patient
        PHI without a compliance framework
  - If you ever want to go clinical: that's FDA 510(k) clearance territory,
    requires clinical validation studies, quality systems (ISO 13485),
    and significant capital. Know this exists; don't try to shortcut it.

--------------------------------------------------------------------------------
6.11 DEFINITION OF DONE
--------------------------------------------------------------------------------

  [ ] 2D classifier trained with AUC > 0.85 on held-out patient-level test set
  [ ] Experiment tracking shows every run (W&B or MLflow)
  [ ] Detection microservice serves predictions from a versioned model
  [ ] Chatbot integration: upload -> detection -> plain-language explanation
  [ ] Every response carries the research-only disclaimer
  [ ] Model card documenting: training data, metrics, limitations
